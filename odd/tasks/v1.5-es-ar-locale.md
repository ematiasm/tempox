# v1.5-es-ar-locale — the interface speaks es-AR, and "today" is the shop's today

The second half of v1.5 (`PLAN.md`). The reversal half shipped as a credit note
(`odd/tasks/v1.5-credit-note.md`, merged in PR #42/#43). This slice carries the
es-AR locale: UI language, ARS money and number formatting, dates, and a
server-side day boundary with a real timezone.

Plan context: `PLAN.md` (v1.5 row), `plan-v1.md` decision 6 and decision 12
(all-English naming until es-AR lands), `plan-v1a.md` decision 4 (the en/fr
toggle is the i18n slot) and decision 9 (the timezone is deferred to v1.5).

## Specs

S1. **The locale is a frontend concern, with one exception: the day.** The wire stays locale-free — money remains a decimal string with two decimals (`"1234.56"`), timestamps remain ISO 8601 UTC instants, enums remain `unit` | `g` | `ml` and `confirmed` | `cancel`. No backend response gains a translated string. The one thing the server owns is the calendar: which window of instants is "today" for this shop. Error messages are translated in the client by HTTP status, not on the server.

S2. **Two languages: `es-AR` (default) and `en`.** `fr` is removed: `fr.ts` is deleted, `Lang` becomes `'es-AR' | 'en'`, and the rail's two-state toggle stays exactly as it is (it shows the label of the other language). A reload always starts in `es-AR` — the choice is not persisted (no cookie, no storage). This supersedes `S13` of `v1.5-credit-note.md`, which required every new string in `en.ts`, `fr.ts` and `types.ts` together.

S3. **One dictionary type, two complete dictionaries.** `types.ts` declares every key once; `en.ts` and `es.ts` both satisfy it, and the key sets are identical — no key exists in one and not the other. `svelte-check` fails the build if a dictionary is missing a key or has an extra one.

S4. **Money is formatted by the active locale, and the wire format never moves.** In `es-AR`: `$ 1.234,56`, `$ 0,00`, negatives as `-$ 1.234,56` (the minus before the symbol, matching `Intl`), grouping `.`, decimal `,`. In `en`: `$1,234.56`, `$0.00`, `-$1,234.56`. Formatting stays exact — it never round-trips the amount through a `number`; the integer part is grouped and the two fraction digits are emitted verbatim (`money.ts` keeps its `BigInt` path).

S5. **Amount input is parsed per locale, and always emits the en-US wire form.** `parseAmount` accepts, and only in `es-AR`: `1234,56`, `1.234,56`, `1.234`, `0,01`, and a leading `$`. It rejects a value it cannot read unambiguously (`1.234,5,6`, `1,234.56` under `es-AR`). Whatever it accepts it returns as `"1234.56"` — two decimals, `.` as the decimal separator. A value it rejects is never sent: the existing "a field does not hold a valid number" path already refuses to record. In `en` the accepted forms stay exactly what they are today.

S6. **Dates and times follow the active locale.** The ledger's day chip and the `time` of each document and credit note are formatted with the active locale's `Intl` formatter, not a hardcoded `'en-US'`. `es-AR` renders the chip as `16 oct 2026` and the time as 24-hour `22:05`; `en` keeps `Oct 16, 2026` and `22:05`.

S7. **"Today" is the shop's day, computed by the server.** A new endpoint `GET /api/day?at=<ISO 8601 instant>` returns `{"from","to","prev","next","zone"}` — four ISO 8601 UTC instants plus the IANA timezone name the window was computed in. `from` is inclusive, `to` is exclusive, and they are the local midnights of the shop's timezone: the same contract `dayRange` already implements on the client, now authoritative. Absent `at`, the server uses its current instant. The timezone comes from the server's configuration (`SHOP_TIMEZONE`, default `America/Argentina/Buenos_Aires`), never from a request parameter. `zone` is returned because the client must render each document's time in the timezone its day was scoped in; without the name it can only guess from the browser's clock, which is the defect this slice exists to remove (see S19).

S8. **The client asks the server what day it is.** `Ledger.svelte` obtains its range from `GET /api/day` (`at` = the instant the page is scoped to) instead of computing local midnights from the browser's clock, and paging a day forward or backward moves the scoped instant by one local day. If the request fails, the ledger shows its existing read error and does not invent a range from the browser's clock: a range the shop did not agree with is worse than no range.

S9. **A malformed `at` is the client's fault, not a 500.** `GET /api/day?at=not-a-date` answers `400` and writes nothing. A well-formed instant is accepted with or without a timezone offset.

S10. **Every visible string comes from the dictionary — including the ones that escaped it.** The strings currently hardcoded in components join the dictionary: `ProductPicker.svelte` (placeholder, `aria-label` of the field and of the listbox, "Searching…", "Search failed", "No product matches that name", "No products yet…", and the `{stock} in stock` suffix), `+layout.svelte` (`aria-label` of the rail and of the language toggle), `SaleDraft.svelte` (`<span class="sr">Remove</span>`), and `Ledger.svelte` (`aria-label="Return {name}"`). No user-visible or assistive-technology-visible text in the three surfaces is a bare literal.

S11. **The unit label is localized; the unit value is not converted.** `unit`, `g` and `ml` are formatted for display per locale (`unit` → `unidad` in `es-AR`; `g` and `ml` stay verbatim). No arithmetic anywhere depends on the label, and the API keeps receiving and returning `unit` | `g` | `ml`.

S12. **No string carries a hardcoded amount or currency symbol.** The two dictionary entries that write a figure into prose (`sales_bonus_note`, `sales_bonus_lines_note`) become functions that receive the already-formatted amount, so the locale's formatter is the only source of that figure. A dictionary file contains no `$`, `0.00` or `0,00`.

S13. **The vocabulary is clean in both languages.** In `es-AR`: `walk-in` displays as `Consumidor Final` (the stored value stays `walk-in`), and an annulled sale reads `Anulado`. In `en`: `walk-in` displays as `Walk-in` and an annulled sale reads `Annulled` — the English side stops borrowing the Spanish stamp. The product name `Tempox` is not translated.

S14. **`<html lang>` follows the active language.** The document's `lang` attribute is `es-AR` or `en` to match the rendered text, so a screen reader announces in the language on screen. `app.html` no longer pins `lang="en"` for the life of the app.

S15. **The es-AR dictionary is written as shop vocabulary, not as a literal translation.** Keys keep their existing names (no renaming churn); values are the words an Argentine shopkeeper uses for these actions and figures. Both dictionaries keep their explanatory comments.

S16. **Docs follow the behavior**: `docs/en/architecture.md` (the i18n section, and the new `GET /api/day` row in the API table), `README.md` (the FR/EN line), `PLAN.md` (v1.5 row and Current focus), `PRODUCT.md` (the "English until the es-AR i18n layer lands" constraint is now discharged, and the undecided list loses the locale), and `DESIGN.md` only if the toggle's rendering changes (it does not).

S17. **Test-first per unit, with the existing behavior preserved.** Each unit observes RED before the fix. Every new rule is asserted through its public interface: the exact formatted string per locale, the exact amount string `parseAmount` returns, the exact JSON of `GET /api/day` (keys, ISO shape, adjacency of consecutive days, `from` inclusive / `to` exclusive), the `400` on a malformed `at`, and the `lang` attribute on the document. Existing behavior that shares the code being changed — `formatMoney`/`parseAmount` shapes, `sumAmounts`, `lineTotalAmount`, `formatQuantity`, and the ledger's range behavior — gets one test proving it still holds, and a differential check runs against the base commit wherever a writer is shared.

S19. **A document's time is rendered in the shop's timezone, not the browser's.** The ledger's day is the shop's day (S7), so the figures inside it must be shop-local too, or the page contradicts itself: with the browser on UTC, a sale recorded at 22:30 in Buenos Aires would appear under the correct date but read `01:30`, and the rows would be ordered by a clock the shop never looked at. The client therefore formats each document's and credit note's time with `Intl.DateTimeFormat(tag, { timeZone: zone })`, using the `zone` that `GET /api/day` returned. No offset arithmetic: a fixed offset is wrong on the two days a year a zone changes it, and `Intl` already carries the tz database. When the zone is not yet known (first paint, or a failed day request) the time falls back to the browser's zone, which is the pre-existing behaviour and never invents a figure.

S18. **Every unit ends green and is committed as a work unit** (Conventional Commit) with its tests and docs beside the behavior; each unit's `Risk:` line names any high-risk item it carries, and a unit carrying one gets its own commit so the native review can take it alone. The last slice closes this document.

## Independent verification (2026-10-17)

An independent read-only verifier ran against the branch and returned **two blockers and three risks**, all addressed before closing:

- **Blocker (S6/S19/S8): the day chip was the browser's date.** The rows were correctly scoped by the server while the label above them was formatted from the machine's clock. On a UTC browser the shop's 16 Oct read `17 oct 2026` over 16-Oct rows, and each "Anterior" click moved the label one day while the rows moved two. Fixed: the chip renders `range.from` in `shopZone`, and `LocaleFormat.day` now takes the zone.
- **Blocker (S18): the slice was uncommitted**, so the work-unit commits and `Risk:` lines the spec requires did not exist. Fixed: three commits (`e3da0e4` backend, `25d21f6` locale core, `cf39ad8` components/docs), each with its `Risk:` line.
- **Risk: paging was browser-day arithmetic**, which is not one shop day where a DST change crosses midnight (Santiago, Havana: one click could skip a day or land two back). Fixed: paging moves to `range.prev`/`range.next`, the neighbouring days the server returned. Pinned by a Havana fixture.
- **Risk: raw unit labels** (`/unit`) were still rendered next to localized ones. Fixed: all unit render sites go through `lang.fmt.unit`.
- **Risk: `en.parseAmount` widened** to accept `$ 25.00` (the base refused it). Kept deliberately — it is what makes a figure copied off the screen paste back — and now recorded by its own test rather than left as a silent difference.
- The verifier's `esAR.day(at, SHOP)` probe assumed an API that did not exist yet; it was adopted (with the two-zone comparison that makes it independent of the runner's timezone).

The verifier could not run the integration tests or the e2e suite (both need the owner's stack); those were run by the author against a live PostgreSQL and a real backend build, and are recorded above.

## Defects found and closed during the slice

1. **The price field rejected its own prefill.** `SaleDraft` filled the line's price with the wire form (`25.00`), which the es-AR parser correctly refuses, so the line never parsed and the sale was silently unrecordable — the record button stayed disabled with no message. Found by the e2e suite timing out on a disabled button. Closed with `LocaleFormat.amountInput` (wire → field), which `parseAmount` reads back, and pinned by a round-trip test.
2. **The price field's placeholder taught the wrong shape.** It said `0.00` in a form that reads `1.234,56`; a cashier copying the hint could not create a product. Closed with `LocaleFormat.amountHint`, whose test asserts the parser accepts it.
3. **The day was the shop's but the hours were the machine's.** Found while verifying T4 against a UTC browser. Closed by returning `zone` from `GET /api/day` and formatting each time with `Intl.DateTimeFormat(tag, { timeZone: zone })` (S19), which also survives a zone whose offset changes with the season.
4. **A first attempt at fix 3 was wrong.** Deriving an offset from the day's `from` was measured against Buenos Aires, New York summer and New York winter, found to have the sign inverted and to ignore the target zone, and reverted in full rather than patched. The `zone` field replaced it.

## Process defects (mine, recorded rather than hidden)

- **T1's unit tests were never RED.** `day.rs` was written with its tests in one pass, so the first run was green and proved nothing about test sensitivity. The gap was closed afterwards with mutation checks, which is weaker evidence than an observed RED and is recorded as such.
- **Two e2e failures were my tests, not the code**: a rail locator keyed on a translated `aria-label` (which stops resolving exactly when the language changes, the thing under test), and an unchanged `'Main'` after the rail was renamed. Both fixed by scoping to the element.
- **A subagent's `npx` run left an empty `node_modules/` at the repository root.** It was outside the allowed surfaces, unignored, and would have shown up as untracked noise in the next review; removed after confirming it held only Vite/Vitest cache directories.

L3 (user decision, 2026-10-17, verbatim): "Endpoint de día en el servidor" — `GET /api/day?at=<iso>` → `{from, to, prev, next}`, with the timezone living in the backend's configuration.

L4 (user decision, 2026-10-17, verbatim): "No persistir: es-AR fijo por defecto" — the language choice does not survive a reload; the toggle stays as a dev/QA tool.

L5 (analysis, 2026-10-17): the backend has no human-readable string in any response path except `GET /api/hello` (`backend/src/routes/hello.rs:21`), which is the walking-skeleton demo and is not in the rail. Every other response is data: decimal strings, ISO instants, enums, UUIDs, and bare status codes. That is why "a general locale for the whole software" would have been translation with no object, and why the locale stays in the frontend except for S7's calendar.

L6 (discovery during T4, 2026-10-17): the T4 implementation resolved the day through `GET /api/day` but kept rendering each document's `created_at` with the browser's clock. Measured: a sale at `2026-10-17T01:30:00Z` is 22:30 on 16 Oct in Buenos Aires but renders as `01:30` on a UTC machine, inside a day the server had correctly labelled 16 Oct. S7 was rewritten to return the zone name and S19 was added, because the scoping fix without the rendering fix leaves the page internally inconsistent. A first attempt at fixing it in the client by deriving an offset from the day's `from` was written, measured against Buenos Aires / New York summer / New York winter, and found to have the sign inverted and to format in the browser's zone anyway; it was reverted rather than patched, and the `zone` field replaced it.
