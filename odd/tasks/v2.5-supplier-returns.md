Returning goods to a supplier is the mirror of v1.5's credit note with the
direction reversed: stock leaves, money comes back, and the purchase stays
byte-for-byte as recorded. Purchase **orders** are deliberately out of scope — the
owner's decision of 2026-10-18 defers them to a later slice, and nothing here
anticipates them.

## Specs

S1 a return is a **second document** (`supplier_returns` +
   `supplier_return_items`); the corrected purchase is never written. Its own
   triggers already forbid an edit.
S2 name, unit and price are **snapshotted** from the purchase line the return
   corrects.
S3 the price is the one **paid**, read server-side from the purchase line. There
   is no override: the client never sends a price.
S4 stock **leaves**: one **negative** `stock_movements` row per returned line,
   `reason = 'supplier_return'`, naming both the purchase and the return.
S5 `/api/cash` becomes `sales − credit_notes − purchases + supplier_returns`.
S6 partial and cumulative: several returns per purchase, never more than was
   bought on a line, serialized so concurrent returns cannot both pass.
S7 `GET /api/purchases` carries each purchase's `supplier_returns` (oldest first,
   empty array never absent).
S8 the 404/400/409 ladder matches the credit note's: unknown purchase or a line
   that is not that purchase's is `404`; empty or non-positive quantity is `400`;
   a return beyond what remains is `409`.
S9 a rejected return writes nothing.
S10 immutability is enforced by triggers written in the creating migration, not
    repaired later.
S11 the ledger's coherence rule is re-cut for the fifth reason, with a
    two-sided equality and the pre-check **before** the constraints it protects.
S12 compile-time query checking; `.sqlx` regenerated and committed.
S13 test-first per unit with RED observed; existing behaviour pinned by a test
    where shared code changed.
S14 every integration assertion is self-relative, against the shared development
    database.
S15 docs follow the behaviour, including a worked cash example.
S16 work-unit commits with their tests and docs.

## Ledger integrity (0011) — a scope extension, and why

While designing v2.5's guards, the owner asked why `reason` needed to exist at
all, and whether a movement needed anything beyond its foreign keys. That question
exposed two defects the six constraints could not see, both measured on the live
schema before anything was written:

1. **A movement's product need not be on the document it names.** A
   `supplier_return` movement for a product that is not in the purchase was
   **accepted**, and so was a `credit_note` movement for a product that is not in
   the sale. The ledger accepted a movement explaining stock the document never
   touched.
2. **A child document need not belong to its parent.** A credit note belonging to
   sale B could be attached to a movement naming sale A. The foreign key proves
   the note exists, never that the pair agrees.

And the structural cause: `reason` is enumerated in **seven** places (one
`reason_known` plus six coherence/direction constraints), so every migration that
adds a reason has to touch three or four of them. `0007`, `0009` and `0010` all
did, and each had to re-write a constraint that the previous one had hardcoded.

### What `0011` does

One trigger, `ledger_movement_is_coherent()`, that derives the rule from the row's
own **shape** instead of naming the reasons:

| shape | reason implied | direction |
|---|---|---|
| no document | `initial` | either |
| `sale_id` | `sale` | negative |
| `sale_id` + note | `credit_note` | positive |
| `purchase_id` | `purchase` | positive |
| `purchase_id` + return | `supplier_return` | negative |

Plus the two rules the constraints never had: the product must be on the document,
and the child document must belong to its parent.

`reason_known` and `quantity_check` stay. The first is the one legitimate place to
list the vocabulary — a closed domain has to be stated somewhere — and it gives a
typo a clear error instead of a shape mismatch. The second is unrelated.

**The six enumerated constraints are dropped**, only after the trigger exists, so
there is no window in which the ledger is unguarded.

#### The defect the e2e found: `PUBLIC_API_BASE` never reached the bundle

Both new specs failed first with a **500 page**, and the browser's console said
`e is not iterable`. The component was iterating `row.supplier_returns` and
receiving `undefined`.

The cause was two layers away from the symptom. `api.ts` reads
`import.meta.env.PUBLIC_API_BASE` with a fallback to `:3001`, but **Vite only
exposes prefixes it was told about**, and `@sveltejs/kit` 3.1.0 sets no
`envPrefix` in this project — so `PUBLIC_` was not among them and the expression
compiled to `undefined` on every build. Measured on the emitted bundle, not
inferred: after a build given `PUBLIC_API_BASE=http://localhost:3099`,
`.svelte-kit/output` contained only `localhost:3001` and no trace of 3099. Adding
`envPrefix: ['VITE_', 'PUBLIC_']` and rebuilding put 3099 there, with 3001 left
only in the fallback.

**Why it survived until now:** in CI the fallback is the correct value. The e2e
job sets `PUBLIC_API_BASE: http://localhost:3001` and the backend really is on
3001, so the variable was decorative and its absence could not fail. Locally the
port points at whatever container holds it, so the e2e silently talked to a stale
container that does not send `supplier_returns` — and the failure surfaced as a
wall of `undefined` fields rather than as a connection error.

This is the generalisable lesson: **when a fallback happens to equal the
configured value, the configuration is untested.** The test suite could not tell
the two apart, and nothing else pointed at it.

#### B1 — a zero on one line cancelled the whole return

The return field was read with `parseQuantity`, which is right for a quantity you
sell and wrong here: it answers `null` for `0` and for a blank, because zero units
is not a movement. On a return form zero is how the operator says *"nothing from
this line"*. One emptied field turned the plan to `null`, no request left, and the
screen reported an invalid quantity.

**Measured**: a purchase of 2 units of one product and 3 of another, returning
only the second, produced **zero POSTs** and the alert *"Una cantidad a devolver no
es válida"*. The only return the screen accepted was *every line, all of it* — the
rarest case, and not what S6 means by partial.

`parseReturnQuantity` reads blank and `0` as zero, a positive whole number as
itself, and refuses a fraction, a sign, a separator or a letter. RED observed
through the UI first; five unit tests pin the parser.

**Why the suite missed it**: both e2e written with the feature returned a
purchase's *only* line, so "all of it" was the only path they exercised. The gap
was not in what the tests asserted but in what they chose to do.

#### B2 — the spec titled "(S8, S9)" proved neither

It read the catalog row with `toContainText('3')`, which also matches the product
name — generated from a base36 timestamp, so it holds a digit like `3` in roughly
6% of runs. Worse, measured directly: with the stock cell reading `"0"`, the row
still contained `"0"` **because the price renders as `$ 10,00`**. The assertion
could not fail for the reason it was written.

And it never contacted the server: the form refuses a plan the server would answer
`409` to, so no request leaves. S9 ("a rejected return writes nothing") is about
what the database does, and no database saw it. The test is now titled for what it
proves, asserts the `.stock` cell, and S9 is left to the backend integration tests
that actually exercise it.

#### The five risks

1. **A recorded return reported itself as not recorded.** `createSupplierReturn`
   succeeded, then `reload()` threw, and the catch wrote the refusal prefix. The
   operator saw "No se devolvió" while the server held the return, stock had moved
   and the form still showed the old quantity — and their natural retry would
   either be refused by the guard or return the goods twice. The two outcomes are
   now separate state, and the "recorded but not re-read" case speaks in soft ink.
2. **One row's error appeared under every expanded row.** `confirming`, `returning`
   and `returnError` were component-level. All three are now keyed by purchase id.
3. **A slow reload undid the user's paging.** `reload()` wrote `range`/`rows` with
   no guard, unlike the effect; measured, paging to the previous day while a
   delayed reload ran flipped the label back to today. Both paths now take a
   generation number and discard anything overtaken.
4. **The day was read by two copies of the same three lines**, and only the effect
   had cancellation and error handling. There is now one `loadDay`.
5. **`createPurchase` was typed as `{purchase, items}`** while the server answers
   `supplier_returns` too. The type described the server wrongly, and the comment
   above the list type claimed both endpoints answered the same shape.
