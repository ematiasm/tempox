Returning goods to a supplier is the mirror of v1.5's credit note with the
direction reversed: stock leaves, money comes back, and the purchase stays
byte-for-byte as recorded. Purchase **orders** are deliberately out of scope — the
owner's decision of 2026-10-18 defers them to a later slice, and nothing here
anticipates them.

## Specs

S1 a return is a **second document** (`supplier_returns` +
   `supplier_return_items`); the corrected purchase is never written. Its own
   triggers already forbid an edit.
S2 name, unit and price are **snapshotted** from the purchase line the return
   corrects.
S3 the price is the one **paid**, read server-side from the purchase line. There
   is no override: the client never sends a price.
S4 stock **leaves**: one **negative** `stock_movements` row per returned line,
   `reason = 'supplier_return'`, naming both the purchase and the return.
S5 `/api/cash` becomes `sales − credit_notes − purchases + supplier_returns`.
S6 partial and cumulative: several returns per purchase, never more than was
   bought on a line, serialized so concurrent returns cannot both pass.
S7 `GET /api/purchases` carries each purchase's `supplier_returns` (oldest first,
   empty array never absent).
S8 the 404/400/409 ladder matches the credit note's: unknown purchase or a line
   that is not that purchase's is `404`; empty or non-positive quantity is `400`;
   a return beyond what remains is `409`.
S9 a rejected return writes nothing.
S10 immutability is enforced by triggers written in the creating migration, not
    repaired later.
S11 the ledger's coherence rule is re-cut for the fifth reason, with a
    two-sided equality and the pre-check **before** the constraints it protects.
S12 compile-time query checking; `.sqlx` regenerated and committed.
S13 test-first per unit with RED observed; existing behaviour pinned by a test
    where shared code changed.
S14 every integration assertion is self-relative, against the shared development
    database.
S15 docs follow the behaviour, including a worked cash example.
S16 work-unit commits with their tests and docs.

## Verification log

### T1 (2026-10-18)

- **RED observed first**: the four v2.5 tests failed with
  `relation "supplier_returns" does not exist` — the tables were absent, which is
  the intended reason. The migration was then created (it had to exist for
  `include_str!` to compile) and applied **through the migrator**, never `psql`.
- **A real defect caught by the positive case.** `v2.5_a_return_takes_stock_out…`
  asserts, *before* any refusal, that a coherent `supplier_return` movement is
  **accepted**. It failed against 0009's `stock_movements_purchase_coherent`,
  which is `(reason = 'purchase') = (purchase_id IS NOT NULL)` — an enumeration
  that a return, which legitimately carries a `purchase_id`, violates. This is the
  third time a migration that adds a reason has had to widen a constraint that
  enumerated the vocabulary. Re-cut to
  `(reason IN ('purchase', 'supplier_return')) = (purchase_id IS NOT NULL)`, and
  the file records why.
  - Worth stating plainly: a *refusal-only* test would have passed here. The
    positive case is what turned a silent constraint conflict into a named defect.
- **Re-applying cleanly.** The fix changed an already-applied migration, so the
  checksum no longer matched. The new tables were verified empty first, the
  migration's objects were reversed by hand, its `_sqlx_migrations` row deleted,
  and the migrator applied the corrected file: **10/10**.
- **GREEN**: 4 v2.5 tests pass; the full integration suite is **35 passed, 0
  failed**.
- **Three mutation checks, each measured by dropping a guard, running, restoring:**
  - dropping `stock_movements_supplier_return_is_outgoing` →
    `a positive supplier_return movement was allowed`
  - replacing the equality with a one-sided rule →
    `a sale movement carrying a supplier_return_id was allowed`
  - dropping `supplier_returns_immutable` → `supplier_return update was allowed`
- `cargo test --bins`: 29 passed. `make sqlx-check`: passes. `cargo fmt --check`
  and `clippy -D warnings` clean.
- The pre-check ordering is asserted against the migration text by a `#[test]`,
  because an incoherent legacy database is what the shared stack cannot supply on
  demand. It fails if the `DO` block is moved after the constraints.

  the movement query asked for `i64` while `stock_movements.quantity` is

### T3 (2026-10-18)

- The test pins four properties that a shape decision hides:
  - a purchase with **no returns carries an empty array**, never a missing field,
    so a client has one shape to read rather than two code paths for one state;
  - returns are **oldest first**, so a correction reads in the order it happened;
  - each return carries **its own lines**, nested, so a reader expands the
    purchase and then the return without a request per document;
  - the purchase's own `total` is **unchanged by returns** — it keeps what it was
    recorded with, which is the whole point of a compensating document.
- A shell mistake worth recording: two `cargo` invocations were run from the repo
  root instead of `backend/`, where `.env` points at the `postgres` hostname that
  does not resolve from the host. The build failed with a database lookup error
  that had nothing to do with the code. Cargo must be run from `backend/`.

### T4 (2026-10-18)

- **RED observed first**: the return case failed with `left: 0, right: 1000` — the
  return moved the till by nothing, because the query did not know the term.
- **The mutation that matters**: changing `+ supplier_returns` to `−` fails the
  same test with `left: -1000, right: 1000`. Restored afterwards, with the sqlx
  cache regenerated for the restored SQL — a mutated query text is a different
  cache key, so restoring means regenerating.
- **The sale and purchase directions are asserted in the same test**, and that is
  deliberate: a sign error in any of the four terms yields a plausible number, so
  each direction has to move the figure by exactly its own amount.
- **Two v1 tests failed on the change again, and it was expected this time.**
  `v1_5_cash_still_counts_every_confirmed_sale_and_nothing_else` and
  `v1_read_endpoints_reflect_writes` both restate the cash rule; both were missing
  the returns term. The evidence that this was the semantic change and not a
  regression: both were off by the same amount, and the cash total is a sum the
  tests can recompute independently.
  - This is the **second** time these two tests had to grow a term (v2 added
    purchases, v2.5 adds returns). They are updated the same way: restating the
    full rule, never copying the query. A test that mirrored the query would agree
    with a wrong query.
  - The pattern is worth naming for whoever adds the fifth term: **`/api/cash` is
    now a four-term sum, and every slice that changes it must update these two
    tests in the same commit.**
- `cargo test --bins`: 29 passed. `make sqlx-check` passes; `fmt` and
  `clippy -D warnings` clean.
