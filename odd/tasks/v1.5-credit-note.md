# v1.5-credit-note — reversing a sale with a credit note

Outcome: the shop reverses a mistaken sale — in full or in part — by emitting a credit note: a new document that returns stock and money, never an edit of the sale it corrects. The reversal action lives inside the expanded document on `/sales`.
Specs authority: this document. Plan context: `plan-v1.md` (decision 6, decision 22) and `PLAN.md` (v1.5 row). The es-AR locale half of v1.5 is **not** in this slice.

## Specs

S1. **A credit note is a new document, never an edit.** The corrected sale keeps every byte: `sales.status` stays `'confirmed'`, `sales.reversed_at` stays `NULL`, `sales.total` and `sales.customer_id` are never written. New tables hold the correction:

- `credit_notes(id uuid pk, sale_id uuid not null fk → sales, total numeric(14,6) not null, created_at timestamptz not null default now())` with `CHECK (total >= 0)` and `CHECK (total = round(total, 2))` — the same money contract as `sales.total` (`0006`).
- `credit_note_items(id uuid pk, credit_note_id uuid not null fk → credit_notes, sale_item_id uuid not null fk → sale_items, product_id uuid not null fk → products, product_name text not null, quantity integer not null CHECK (quantity > 0), unit_price numeric(14,6) not null CHECK (unit_price >= 0), line_total numeric(14,6) not null CHECK (line_total >= 0), unit text not null CHECK (unit IN ('unit','g','ml')))` — name, unit and price are snapshots of the corrected line. `line_total = quantity * unit_price` and `credit_notes.total = SUM(its items' line_total)` are write-path invariants, unchanged from the sale path.

S2. **History guards extend to the new tables**, in the same style `0003`/`0004` established: `credit_note_items` reject `UPDATE` and `DELETE`; a note's economics (`sale_id`, `total`) are immutable. Nothing the correction touches is ever edited afterwards; a wrong credit note is corrected by another compensating document, not by rewriting this one.

S3. **Partial and cumulative refunds.** `POST /api/sales/{id}/credit-notes` takes `{"items":[{"sale_item_id":"<uuid>","quantity":<int>}]}`. A line's cumulative refunded quantity (`SUM(quantity)` over every `credit_note_items` row for that `sale_item_id`) may never exceed the quantity sold on that line. Several notes per sale are allowed while the sums hold.

S4. **Refunds are serialized per sale.** Inside the transaction the handler takes the sale's row lock (`SELECT ... FOR UPDATE` on `sales`) before reading the cumulative refunded quantities. Two concurrent refunds of the same sale therefore cannot both pass the guard and over-refund a line. The lock is taken first, before any read of refunded sums.

S5. **One transaction.** The note header, its items and one **positive** `stock_movements` row per refunded line land together or not at all — the mirror image of the sale path, whose movements are negative.

S6. **The ledger's reason grammar gains exactly one value: `'credit_note'`.** `stock_movements` receives a nullable `credit_note_id uuid fk → credit_notes`, and the coherence constraints become: `reason IN ('sale','credit_note') → sale_id IS NOT NULL`; `reason = 'credit_note' ⇔ credit_note_id IS NOT NULL`; `reason = 'initial' → sale_id IS NULL AND credit_note_id IS NULL`. The append-only trigger is untouched: a refund appends rows, it never edits the movement it reverses.

S7. **Errors, distinct and honest.** `404` unknown sale, or a `sale_item_id` that does not belong to that sale. `400` empty `items`, or a `quantity` of zero or less. `409` a refund that would exceed the quantity sold on a line. A rejected request writes nothing: no note, no note items, no movements, and `/api/cash` is unchanged.

S8. **`GET /api/sales` carries the correction.** Every sale in the list gains `credit_notes`, an array (oldest first) of `{id, sale_id, total, created_at, items:[{id, credit_note_id, sale_item_id, product_id, product_name, quantity, unit_price, line_total, unit}]}` — `total`, `unit_price` and `line_total` as decimal strings with two decimals, like every other amount. A sale with no note carries an empty array, never a missing field.

S9. **Cash is net of credit notes**: `GET /api/cash` returns `{total}` = `SUM(sales.total WHERE status = 'confirmed') − SUM(credit_notes.total)`. Fully bonified sales (`total = 0`, `0005`) and bonus lines stay exactly as they are: a refund returns what was charged, which for a bonus line is `0.00`.

S10. **The reversal action lives inside the expanded document.** On `/sales`, opening a document's lines reveals, below the lines table and visually separated from it, the reversal action. Confirming it is an inline two-step (`Anular venta…` → `[Sí / No]`) — a single click never emits a credit note. Undoing a confirmed note is out of scope.

S11. **Per-line refund quantities.** The expanded lines table gains a refund-quantity field per line, prefilled with the line's remaining (unrefunded) quantity. A line already fully refunded offers no field and cannot be refunded again.

S12. **The day shows the correction under the sale, not as a new row.** The sale keeps its row; a fully refunded sale wears the existing `Anulado` stamp and its total stays struck through (`Ledger.svelte:120`, `Stamp.svelte`); a partially refunded sale keeps its `Confirmed` stamp. Under the expanded lines, each credit note renders as its own block: `Nota de crédito NC-#<id:8>  −<total>  <time>`, followed by its lines. The annulment figure at the page's foot (`sales_annulment*`) is replaced by the day's real refunded total, or removed if it cannot be derived honestly.

S13. **Every new string lands in `en.ts`, `fr.ts` and `types.ts` together.** Both languages stay maintained; the stamp label stays `Anulado`.

S14. **Docs follow the behavior**: `docs/en/architecture.md` (route table, invariants, "events are immutable → corrections are compensating rows" now has a real second document) and the same section of `README.md` that describes the sales slice.

S15. **Test-first, per unit.** Each unit observes RED before the fix, and each new guard's test asserts every observable effect of the rule it covers: the exit/status code, the exact wire shape, and that a rejected refund leaves stored data — notes, note items, movements and the cash total — unchanged. An existing behavior counts as touched when it shares the code changed (the sale create path, `/api/sales` list shape, `/api/cash`, the ledger's expansion, the stamp); each of those gets one test proving its previous behavior still holds, and a differential check against the base commit is run where the change shares a writer.

S16. **The stamp and the confirm are e2e-verified.** `frontend/tests/e2e/sale.spec.ts` gains the reversal flow: record a sale, refund it partially, refund the rest, and assert the document wears `Anulado` — the stamp is the one piece of the direction no unit test can see (v1a's L5, S14).

S17. **Every unit ends green and is committed as a work unit** (Conventional Commit) with its tests and docs beside the behavior; the last slice closes this document.
