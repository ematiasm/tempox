# Architecture — Tempox

## Opinionated choices

### 1. Axum over Actix

Axum aligns with the tokio + tower ecosystem and has become the de-facto standard for new Rust HTTP services. Its extractor-based API is easy for beginners while remaining flexible.

### 2. sqlx over Diesel or SeaORM

- Raw SQL kept close to the code (no query DSL to learn).
- Compile-time query checking (via `sqlx::query!`) against a live database. The `sqlx::query!` macros resolve while the crate compiles, so CI runs a PostgreSQL service and applies the migrations before the first build step.
- Async-native, no blocking pool.

### 3. SvelteKit 5 with runes

- Reactive primitives are explicit (`$state`, `$derived`, `$effect`) — easier to reason about than legacy stores.
- Zero-config TypeScript.
- Server- and client-side rendering in the same file, with the option to add server actions later.

### 4. Docker Compose as the single entrypoint

- One `docker compose up` covers db + backend + frontend + adminer.
- Same commands work on Linux, macOS, and Windows (via WSL2).

### 5. i18n via a runes-backed class

- No i18n library dependency.
- Language state is a single `$state`-holding class; components read `lang.t.<key>` for words and `lang.fmt.<...>()` for money, quantities and dates.
- **Two languages: `es-AR` (default) and `en`.** The choice is deliberately not persisted — the shop opens in its own language every time, and the toggle exists so a developer can read the English side. `fr` was a placeholder that proved the slot worked and was never a product requirement.
- **The locale is a frontend concern with exactly one exception.** The wire stays locale-free: money is a decimal string with two decimals (`"1234.56"`), timestamps are ISO 8601 UTC instants, enums stay `unit|g|ml` and `confirmed|cancel`, and no response gains a translated string. Error messages are translated in the client by HTTP status. The exception is the calendar: which window of instants is "today" is a fact about where the shop is, not about how the browser was installed, so `GET /api/day` owns it (`SHOP_TIMEZONE`) and the client renders each document's time in the zone that endpoint names.
- **Both directions of money are per locale.** `formatMoney` writes `$ 1.234,56` in es-AR and `$1,234.56` in en, without ever parsing the amount into a float. `parseAmount` reads what the active language types and always returns the wire form; a value it cannot read unambiguously (`1,234.56` under es-AR) is refused rather than guessed, because the value it feeds becomes an immutable sale line. Anything that pre-fills an amount field goes through `amountInput`, so what the form shows can always be parsed back.
- Fine for starter-scale apps; swap in `svelte-i18n` if you outgrow it.

## API surface (v1 — sales, v1.5 — reversal and locale, v2 — purchases, v2.5 — supplier returns, v3 — accounts and payment methods, v4 — money that is owed, v5 — a party's account and collecting against it)

**The table below documents the routes a screen calls.** The v4 write routes — `POST
/api/opening-balances`, `/transfers`, `/count-adjustments`, `/payments`, `/settlements`,
`/payable-settlements` — are served and tested but have **no screen yet**, by the owner's
API-only decision for that slice; their contracts live in `odd/tasks/v4-settlement.md`,
`v4-receivables.md` and `v4-payables.md`. They are named here so the omission is a documented
boundary rather than a reader's surprise, and they join the table when the slice that gives
them a screen lands.

| Route | Purpose |
|---|---|
| `GET /api/products` | Products with stock derived from the movement ledger |
| `POST /api/products` | `{name, list_price, unit?, initial_stock?}` — creates the product; an `initial` movement is seeded only when `initial_stock > 0` |
| `GET /api/customers` | Customers, including the seeded `walk-in` |
| `POST /api/customers` | `{name}` — 409 on duplicate name |
| `GET /api/suppliers` | Suppliers, including the seeded `one-off-supplier`. Listed like any other, because a purchase without a named supplier names it explicitly and a picker that hid it would make that fallback invisible |
| `POST /api/suppliers` | `{name}` — 400 on a blank name (trimmed first), 409 on duplicate. No edit and no delete: a purchase that named a supplier is history |
| `POST /api/sales` | `{customer_id?, payment_method_id?, items: [{product_id, quantity, unit_price?}]}` — **one transaction**: the sale, its lines (name/unit/price snapshots), and one negative stock movement per line. Omitted `customer_id` → walk-in; omitted `payment_method_id` → the seeded `cash` method; omitted `unit_price` → list price. 404 an unknown method. `\"on_account\"` instead of an id means the sale moved no money and owes, and it is refused with `400` when the sale names `walk-in`: anonymous debt is not debt. The server reads the method's account rather than trusting a client-supplied one — the client names the method, the method knows its account. A `unit_price` of `0` is a bonus line (regalo): it is recorded, the stock still drops, and it contributes nothing to cash. 404 unknown product/customer; 400 empty, non-positive quantity, or negative price |
| `GET /api/sales?from=&to=&limit=50&offset=0` | Sales newest first, with nested lines, customer name, and `credit_notes` (oldest first, each with its `items`; an empty array when the sale was never corrected). `from` is inclusive and `to` is exclusive, so adjacent ranges partition the ledger instead of double-counting the sale recorded at midnight; absent bounds keep the unscoped recent-documents behaviour. `offset` defaults to `0`, clamped up to `0` so a negative value is not a 500. The limit is clamped to 1..200, so `limit=0` returns one sale rather than none |
| `POST /api/sales/{id}/credit-notes` | `{payment_method_id?, items: [{sale_item_id, quantity}]}` — **one transaction**: a credit note, its lines (name/unit/price snapshots of the corrected sale line), and one **positive** stock movement per line. Reverses part or all of a sale; several notes may follow while each line's cumulative refunded quantity stays within what was sold. 404 unknown sale or a line that is not that sale's; 400 empty items or a non-positive quantity; 409 a refund that would exceed the quantity sold. Concurrent refunds of one sale are serialized with `SELECT ... FOR UPDATE`, so two notes cannot both pass the cumulative guard. Omitted `payment_method_id` **inherits the corrected sale's method**, which is what makes a refund of a sale on account move no money: the note inherits the sale's `NULL` and lowers the obligation instead. An explicit method may be named for a sale already collected, and it must be a rail that actually received the money, less what earlier notes already took back (`409` otherwise) |
| `POST /api/purchases` | `{supplier_id?, payment_method_id?, items: [{product_id, quantity, unit_price?}]}` — **one transaction**: the purchase, its lines (name/unit/price snapshots), and one **positive** stock movement per line. Omitted `supplier_id` → `one-off-supplier`; omitted `payment_method_id` → the seeded `cash` method; omitted `unit_price` → list price. 404 unknown product/supplier/method; `\"on_account\"` means the purchase owes the supplier, and it is refused with `400` for the one-off supplier; 400 empty items, a non-positive quantity, or a line total finer than a cent (a price of `0.005` with quantity 1 is refused; with quantity 2 the line total is `0.010`, which is whole cents, so the handler accepts it and the database's own whole-cents check rejects it as `500` — the same shape the sale path has). A rejected purchase writes nothing: every line is resolved before the first write, so an unknown product later in the list leaves the earlier ones unwritten too |
| `GET /api/purchases?from=&to=&limit=50&offset=0` | Purchases newest first, with nested lines and `supplier_returns` (oldest first, each with its `items`; an empty array when the purchase was never returned, never an absent field). The same half-open `[from, to)` contract, the same `limit` clamp (1..200) and the same `offset` clamp as the sales ledger — a day filter that meant one thing on one screen and another on the next would be a bug that reads as a UI fault |
| `POST /api/purchases/{id}/supplier-returns` | `{items: [{purchase_item_id, quantity}]}` — **one transaction**: the return, its lines (name/unit/price snapshots of the corrected purchase line), and one **negative** stock movement per line. Returns part or all of a purchase; several returns may follow while each line's cumulative returned quantity stays within what was bought. The client sends **no price**: what the return is worth is read from the purchase line, so a return can never be worth more than the purchase. 404 unknown purchase or a line that is not that purchase's; 400 empty items or a non-positive quantity; 409 a return beyond what the line has left. Concurrency is serialized with `SELECT ... FOR UPDATE` on the purchase, and the running total is summed inside the request so a request naming the same line twice is judged on its total |
| `GET /api/accounts` | Accounts with their methods nested and each account's **derived balance** (a two-decimal string, summed over `money_movements` for all time), default first. This is where the till's figure lives since `GET /api/cash` was retired in v3 |
| `POST /api/accounts` | `{name}` — `409` duplicate, `400` blank (trimmed first). **`is_default` is refused**: a new account has no payment methods, so it cannot be the till. Create it, attach a method, then promote it through `PATCH` |
| `PATCH /api/accounts/{id}` | `{name?, is_default?}` — promoting clears the previous default **in the same transaction**, because the database guarantees exactly one at commit. An empty body is `400`; an unknown id is `404` |
| `GET /api/payment-methods` | Every method, **including inactive ones**: a ledger rendering a historical document needs the name of a method retired after the sale |
| `POST /api/payment-methods` | `{name, account_id}` — `404` unknown account, `409` duplicate name (unique globally, so a picker never offers two entries the cashier cannot tell apart), `400` blank |
| `PATCH /api/payment-methods/{id}` | `{name?, is_active?, account_id?}` — renaming is a correction (every document stores the id, so a rename moves no balance); `account_id` is refused with `409` once any document names the method, because moving it would rewrite yesterday's balance today |
| `GET /api/day?at=<instant>` | `{from,to,prev,next,zone}` — the shop day containing `at` (ISO 8601 UTC instants; `from` inclusive, `to` exclusive) plus the IANA `zone` it was computed in, taken from `SHOP_TIMEZONE` (default `America/Argentina/Buenos_Aires`). Absent `at` means now; a malformed `at` is `400`. The zone is server configuration, never a query parameter, and it is returned because the client renders each document's time in it — a browser only knows its own |
| `GET /api/customers/{id}/account` | A client's account in **one response**, under one `REPEATABLE READ` snapshot so its three boxes describe the same instant: `{id, name, owed, in_favour, unpaid_sales:[{id, source_document_id, total, outstanding, occurred_at}]}`. **The two figures are never netted** — a client can owe 1000 and hold 500 at once, and one number would destroy both. `id` on an unpaid document is the **obligation**, `source_document_id` is the **sale**; they are different rows and only the second is a document a cashier can look up. `404` for an unknown id — never zeros, because "owes nothing" and "is not there" are different statements |
| `GET /api/suppliers/{id}/account` | The mirror: `{id, name, owed_to_them, in_our_favour, unpaid_purchases:[...]}`. The fields are named differently on purpose — one shared name would let a screen label "what we owe" as "what they owe" |
| `POST /api/customers/{id}/collections` | `{payment_method_id, total, manual: [{debt_id, amount}]}` — **one transaction**: one `payments` row, **one** ledger entry signed by the direction, and one settlement per debt the money answers. `debt_id` is the **`id` of an unpaid document in the account payload** (the obligation), not the sale. `manual` is the cashier's own allocation and may be empty; **what it does not name the rule spends, oldest document first**, and a debt named by hand is excluded from that walk (one settlement row per pair, one `source` per row). Money left after every debt is the party's credit balance, not an error. Every manual amount is whole cents and positive, and must belong to a debt of **that** party: `400` otherwise. `409` when the manual lines exceed `total`, when a line exceeds its own debt's `outstanding`, or when two collections race for the same room. `404` for an unknown party or method. **Answers `201` with `{payment_id, total, direction, applied:[{debt_id, amount, source, debt_outstanding}], unapplied, account}`**, where `source` is `manual` or `oldest` and `account` is the exact payload the matching `GET …/account` returns — read **in the same transaction**, so a panel replaces its state instead of asking again |
| `POST /api/suppliers/{id}/payments` | The mirror, with the direction reversed (`out`, and the ledger entry negative): the debts are `payables` and the settlements `payable_settlements`. The figures invert (`owed_to_them`, `in_our_favour`), and a client's obligation is refused with `400` because it is not a payable. The remaining difference is structural rather than an omission: a customer's overpayment becomes a refundable balance and a supplier's does not — `payments_direction_matches_party` makes `in` from a supplier inexpressible, so the supplier side has two terms in its balance where the customer side has three |

Request decoding is axum's `Json` extractor, so its rejections keep their standard codes: `415` without a JSON `content-type`, `400` on malformed JSON, and `422` when the shape parses but a field is wrong (an unparseable UUID, a missing field, `"quantity": "two"`). The handler's own validation answers `400`.

### Invariants enforced by the database

- **Every document says where its money moved — or says it moved none, and a trigger holds
  that claim**: `payment_method_id` is `NOT NULL` on `credit_notes` while `sales`, `purchases`
  and `supplier_returns` are nullable since v4, where the null is not a free pass but half of a
  rule enforced at commit: a null document must be named by exactly one obligation (`sales`) or
  one payable (`purchases`) and write no ledger entry, while a document that names a method must
  write at least one entry and acquire no debt. A payment method belongs to exactly one account,
  an account has zero or more methods, and an event names the **method** — the method resolves the
  account. The direction is the requirement: a method shared across accounts would make every
  per-account balance unreconstructable. A method's `account_id` is immutable once any document
  names it, because moving it would rewrite yesterday's balance today; renaming is allowed and
  **corrects** history, since documents store the id and the name is read by join.
- **A debt is a document, not an account, and there is no account for it**: the `credit` account and method are **not in the schema at all** since v4's `S7` — removed from the initial seed rather than deleted by a migration, because nothing has shipped. A ledger row naming a method whose account is not `cash` or `digital` is refused by trigger, and `accounts.kind` is that closed set. What a customer owes lives in `obligations` (with `obligations_adjustments` when a credit note lowers it and `settlements`
  when money arrives) and what the shop owes a supplier lives in `payables` (with
  `payables_adjustments` and `payable_settlements`). Both are append-only, both write no ledger
  entry of their own, and the two ceilings on each side are sums over rows — a debt may be paid
  in parts, a payment may cover several debts, and a debt may not be resolved twice, once by a
  document and once by money. The supplier side was given its own tables rather than extending
  `obligations`, so no migration has to `ALTER` a closed set or `CREATE OR REPLACE` a ceiling
  that already guards money (`odd/tasks/v4-settlement.md` L25, `odd/tasks/v4-payables.md`).
- **A party's account is read as one document, under one snapshot.** `GET /api/customers/{id}/account` and its supplier mirror return identity, both balance figures and the unpaid documents together, in a single `REPEATABLE READ READ ONLY` transaction. Read separately, a collection landing between the balance and the list would let the panel show "owes 0.00" above a sale with 40 outstanding — the contradiction a one-response endpoint exists to prevent. **The two figures are never netted**: what is owed and what is held in the party's favour are two subtractions over two different sets of rows, and a client can be on both sides at once. An unpaid document carries the **obligation's** `id` and the **sale's** `source_document_id`; they are different rows and only the second is the one a cashier can look up.
- **One document moves the money, and as many rows as it can answer.** `POST /api/customers/{id}/collections` and its supplier mirror write the payment **and** its ledger entry **and** every settlement in one transaction, so a refusal leaves nothing behind — which matters because the ledger is append-only and a payment for a rejected request cannot be taken back row by row. **The settlements write no ledger entry**: the money moved when the payment was recorded, and an entry per settlement would count the same coin again. The rule that decides which debts the remainder answers is stated once, in `routes::collections::plan`, and **the client does not reproduce it** — the form shows `total − manual` as a figure and a sentence, and the response's `applied` with its per-row `source` (`manual` or `oldest`) is the only statement of what happened. A cashier typing a split therefore sees which documents closed and *why*, and a client that predicted the allocation would be a second implementation of one rule.
- **One lock order for a party's money, and it is the one every writer agrees on**: the party's `payments` rows first, then its debts in ascending `(occurred_at, id)`. The order is not free to choose — the schema's own settlement trigger locks the payment and then the debt, so a route that took them the other way round would cycle against it (`aa95665` records that cost). Debt rows are locked before the first ceiling is judged, so two concurrent collections cannot each read the same committed sums and both find room.
- **Balances are derived from one view**: `money_movements` is a `VIEW`, one row per **effect** on an account, with the sign declared once (positive is money entering). A sale adds, a credit note subtracts, a purchase subtracts, a supplier return adds. It stores nothing, cannot drift from the documents, and needs no backfill; a view rather than a `SUM` per call site because four consumers exist and credit will make seven or eight, and a hand-written `UNION` that forgets a branch returns a plausible wrong number instead of an error — the defect `0011` killed for stock. An account balance is `SUM` over this view, **never a column**.
- **The default account is configuration with two consumers**: the `/sales` footer and the sale picker's default. The partial unique index guarantees at most one true; a `DEFERRABLE INITIALLY DEFERRED` constraint trigger guarantees exactly one **at commit**, so moving the till is two statements in one transaction rather than the ordering puzzle a `BEFORE` trigger would impose. A new account is never born the default: it has no methods, so it is created, given a method, and promoted.
- **Money is exact**: a decimal currency amount with two decimals, guarded by *value* (`v = round(v, 2)`) in a column that declares scale 6, so an over-precise value is refused instead of silently rounded. `line_total = quantity × unit_price` and `sales.total = Σ line_total` are computed by unit-tested pure functions before any write. Amounts are never negative; a price of `0` is allowed, which is how a bonus line (regalo) is recorded.
- **Stock is a ledger**: append-only movements; balances are always derived (`SUM`), never stored. The ledger rejects `UPDATE`, `DELETE` and `TRUNCATE`, and every reason is one of the values the schema knows (`initial`, `sale`, `credit_note`, `purchase`, `supplier_return`), so a balance change always has a nameable cause. A movement for a sale or a credit note must name the document that caused it, a `credit_note` movement must name its note, and a `purchase` movement must name its purchase **and be positive** — stock comes in on a purchase, and the ledger accepts negative quantities in general, so without that rule a purchase could silently remove stock while its document says the goods arrived. A `supplier_return` movement is the mirror: it must name **both** the purchase it corrects and the return, and it must be **negative**, because stock leaves.
- **Events are immutable**: `sale_items`, `credit_notes`, `credit_note_items`, `purchases`, `purchase_items`, `supplier_returns` and `supplier_return_items` reject `UPDATE`, `DELETE` and `TRUNCATE`. A sale's and a note's economics — `total`, `customer_id`/`sale_id`, and `payment_method_id` — are locked by `guard_sale_economics`, which compares them with `IS DISTINCT FROM` rather than `<>`: `NULL <> value` is `NULL`, and an `IF` whose condition is `NULL` does not fire, so the stricter spelling is what keeps the guard guarding if a column is ever relaxed. Every document has **no permitted edit at all** beyond that — a purchase and a supplier return have no status and therefore no transition either.
- **A return is a second document**: a wrong purchase is never edited or deleted, because its guards make that impossible and deleting it would erase a real movement of money and stock. Returning goods appends a `supplier_returns` document that names the purchase it corrects. Whether a purchase is fully returned is **derived** from its returns, never written onto it — the purchase keeps its own `total` and reads as a purchase either way.
- **A return either returns money or lowers a debt, and never both**: a `supplier_return` that names a method brings money back through that rail — and may only name a rail the purchase actually paid, less what its earlier returns already took back, or it is `409`. A return that inherits a purchase on account inherits its `NULL` method: it writes no ledger entry and lowers the payable through a `payables_adjustments` row. The override and its guard arrived together, deliberately: `supplier_returns` had no override and therefore **no hole** until v4 gave it both, and the hole it closes is `v3-accounts.md` L107 mirrored — a return through the till on a purchase paid from the bank drives the till negative for money it never held.
- **A purchase is a fact, not an intention**: `purchases` carries no `status` column, so "the row exists" and "it counts" are the same statement in stock, in cash and in every derived number. A purchase *order* is a different document, still deferred (the owner's decision of 2026-10-18 put supplier returns in v2.5 and left orders for a later slice), and adding it later is a nullable `ALTER TABLE` with no backfill — which is why no reserved column anticipates it.
- **Corrections are compensating rows** (a reversal), never edits. Reversing a sale emits a **credit note** — a second document that returns stock and money — and leaves the sale byte-for-byte as recorded. A partial refund is not an annulment; a sale reads as annulled when its lines are fully refunded, which the client derives from the notes and from nothing else. `sales` carries no lifecycle column at all: v1 reserved `status` and `reversed_at` for a draft/confirmed/cancel/done flow that never happened, nothing but the default ever wrote either, and v3 dropped both. "The row exists" and "it counts" are one statement, exactly as they already were for a purchase.

## What's out of scope for Tempox

- Authentication (add your own auth crate, e.g. `axum-login`, JWT, or an external IdP).
- Observability beyond `tracing` (no Prometheus/OTel here — see `starter-devops`).
- Multi-tenancy / RLS.
- Rate limiting / anti-abuse.

## Suggested first extensions

- Add auth: `axum-login` with a `users` table + session cookie.
- Add a background job queue: `apalis` or `sqlx-based-outbox` for lightweight cases.
- Add OpenAPI: `utoipa` + `swagger-ui`.
